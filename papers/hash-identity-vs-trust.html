A File Hash Identifies Bytes, Not Trust

Cryptographic hashes support reproducible file identification, but they do not establish whether the identified software is trustworthy.

TECHNICAL NOTE 0122 OCTOBER 2026~461 WORDS

Research question

What can an analyst legitimately conclude after computing a cryptographic digest of a game modification? The narrow answer is that a digest identifies a sequence of bytes with extremely high practical reliability when a modern collision-resistant algorithm is used correctly. A hash alone says nothing about the software's origin, permission requests, intended functionality or runtime behavior.

This distinction matters for security scanners because a familiar-looking identifier can become a misleading substitute for evidence. A green status should never follow solely from a digest being absent from a known-malware database.

Threat model and assumptions

Consider two downloaded archives claiming to contain the same mod. An analyst wants to compare them with a developer's release. The relevant questions are whether the files match, whether the developer's reference is authentic, and whether the release itself deserves trust. These are separate decisions.

The model assumes the analyst can compute SHA-256 over the complete files and can access a reference digest from a source whose authenticity must be evaluated. It does not assume that matching the developer's bytes implies that the developer or code is benign.

Evidence layers

A local SHA-256 digest supports exact-byte comparison. A signed release manifest, when verified against a trusted publisher identity, can add provenance. A dated reputation result may contribute historical observations. Structural inspection may identify bundled scripts, native libraries or unexpected archive entries. None of these individual signals is a universal proof of safety.

Evidence should retain its origin, observation time and scope. A report that states only 'hash verified' omits whether the reference came from a trusted source and what, if anything, was assessed about the file's behavior.

Illustrative case, not an experiment

Suppose two fictional mod archives produce the same SHA-256 digest. They are effectively identical for the purpose of routine integrity comparison. If the reference digest was copied from an untrusted mirror, that equality does not establish authentic provenance. If the archives contain an unsafe program, matching hashes merely show that both copies contain the same program.

Conversely, different hashes do not necessarily indicate malicious modification. Recompression, metadata changes or a legitimate new version can alter the bytes. The next step is to identify and explain the difference, not automatically label one copy malicious.

Reporting model

A defensible output separates 'identity', 'provenance', 'static observations', 'external intelligence' and 'unexamined behavior'. For each field, record whether the data was actually collected. A missing observation must not silently become a favorable result.

The recommended language is precise: 'SHA-256 matches the publisher's referenced file; publisher authenticity has not been independently verified' is stronger and more honest than 'verified safe'.

Limitations and next research

This note is a conceptual analysis, not a malware-detection benchmark. It does not estimate false-positive rates, validate signatures, or test live malicious samples. Future reproducible work could compare versioned benign sample sets with known publisher manifests and report agreement rates without implying a security verdict.
