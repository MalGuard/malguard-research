Archive Structure Matters More Than a Filename

An archive's filename is an unverified label. A safer inspection process begins with its actual structure and clearly defined extraction boundaries.

Research question

Which properties of a downloaded mod archive can be assessed without running its contents? Archive inspection can describe entry names, nested paths, uncompressed sizes, compressed sizes, type signatures and the presence of executable or script-capable components. These are observations rather than conclusions about intent.

The main analytical mistake is treating a friendly filename, icon or extension as if it established the file's underlying format or trustworthiness.

Scope and threat model

Game modifications may legitimately contain assets, configuration files, scripts, plugins and native libraries. Attackers can also distribute unwanted code through files presented as game add-ons. An inspection system therefore needs to identify what it sees without assuming that every DLL is harmful or every texture file is safe.

The model considers untrusted archive input, including malformed containers, nested archives and misleading entry names. It does not execute mod files and does not promise to identify all concealed behavior.

A bounded static inventory

First establish the actual container format from file structure, not merely the extension. Next enumerate entries without extraction. Record relative paths, entry counts, sizes, compression ratios and nested package indicators. Anomalies such as absolute paths or traversal-like names deserve explicit attention because careless extraction can write outside an intended directory.

Resource boundaries matter. An archive can declare large expanded content relative to its compressed size. A scanner should impose limits on total expanded size, entry count, nesting depth and time spent parsing, rather than trusting archive metadata without validation.

Interpreting contents in context

A native library in a game plugin package can be expected; a library in a package advertised as image-only content may warrant more scrutiny. A configuration file that names a remote service is not automatically malicious. The meaningful question is whether observed components align with the claimed functionality and the expected installation model.

A scanner should avoid converting a single suspicious-looking entry into a categorical verdict. Explain which component was observed and why it matters.

Illustrative example

Imagine a fictional archive called 'classic-textures.zip'. Its inventory includes image assets, a configuration file and one native library. The filename suggests textures, but the package has executable capability. A careful report would flag the mismatch for review and state that the library was not executed or behaviorally assessed.

If the same structure is documented by a trusted developer for a plugin requiring native code, the interpretation changes. The observed file list remains the same; the surrounding evidence changes.

Safe design implications

Defensive scanners should treat archives as untrusted data, parse with bounded resources, avoid automatic execution, and distinguish observed format from claimed extension. Extraction, when needed, should use a hardened destination and path validation. This article intentionally does not provide an exploitation recipe.

This is a qualitative methodology note, not a measured comparison of archive-analysis products.
